FINDINGS
================================================================================

1. Authentication is NOT the problem. The proxy-injected credential works:
   /links and /links/info both return 200 with full workspace data.

2. Request SHAPE could not be validated, because every /analytics call was
   rejected before any parameter validation ran. All four shapes returned an
   identical 429:
     - groupBy=count, no link filter
     - groupBy=count + domain & key
     - groupBy=timeseries, no link filter
     - groupBy=count + linkId

3. The 429 is NOT a transient rate limit. The response headers say:
       X-Ratelimit-Limit: 0
       X-Ratelimit-Remaining: 0
       X-Ratelimit-Reset:  1790150298000   (epoch ms)
       Date:               Wed, 23 Sep 2026 07:58:17 GMT  (= 1790150297 s)
   The reset timestamp is roughly ONE SECOND after the request. So the window
   resets every second and the allowance in that window is zero. The quota is
   not exhausted; it is provisioned at zero.

4. The limit is endpoint-scoped, not account-wide. In the control test above,
   /links returned 200 at the same moment /analytics returned 429. A shared
   token bucket would have throttled both.

5. A 120-second idle backoff did not help. The first /analytics request after
   that full idle window returned 429 immediately.

CONCLUSION

   Backing off and retrying will never succeed. X-Ratelimit-Limit: 0 means the
   /analytics endpoint is gated off for this workspace, and Dub is reporting
   that gate using a rate_limit_exceeded error rather than a
   plan/permission error. On Dub, the Analytics API is a paid-plan feature;
   this workspace (ws_1M36K6S3843QMFVY6X3XGTM25) appears to be on a tier that
   provisions zero analytics API calls.

   The fix is a plan or entitlement change on the Dub account, NOT a change to
   the request shape, the parameters, or the retry strategy.

   Caveat: this is an inference from X-Ratelimit-Limit: 0 plus the
   endpoint-scoped behaviour. It has not been confirmed against Dub's billing
   settings or support. Confirm the workspace's plan and its Analytics API
   entitlement before concluding the integration code is wrong.

   Interim workaround: the per-link aggregate counters are already present in
   the /links and /links/info responses (clicks, leads, conversions, sales,
   saleAmount, lastClicked). Those cover total-clicks reporting without the
   analytics endpoint. What they do NOT provide is any time-bucketed or
   dimensional breakdown (timeseries, country, referrer, device), which is the
   part that genuinely requires /analytics.
